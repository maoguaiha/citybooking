## 角色与分工（RACI 总表）

> R=负责执行　A=拍板 accountable　C=被咨询　I=被告知

| 阶段 \ 角色 | PM/TL | 前端 FE | 后端 BE | 测试 QA | AI 协作 |
| --- | --- | --- | --- | --- | --- |
| 框架选型（仅 greenfield） | **A** | I | C | I | **R**（搜+对比表） |
| 写需求/PRD（仅 greenfield） | **R/A** | C | C | C | R（辅助） |
| 定级 | **A** | C | C | C | I |
| 写 Spec 五段 | **R/A** | C | C | C（测性） | I |
| 编码 + 风格约束 | A（抽审） | **R** | **R** | I | **R**（辅助写） |
| 单测 | I | R（可选） | **R** | C | R（辅助写） |
| 审查 + Git/PR | **A**（验收） | R（自查） | R（自查） | **A**（红线复核） | R（辅助查） |
| 合并 + 沉淀 | **A/R** | R | R | R（报告） | R（记录） |

**一句话分工**：PM/TL 定「做什么、不改什么、算成功」并定级拍板；FE/BE 按风格约束实现；QA 对红线一票否决并跑运行时验证；AI 是贯穿全程的「加速器」，但**每个技术决策的最终责任在人**。

### 各角色红线（通用，项目特有项从代码 derive 后追加）
- **PM/TL**：「不改什么」必须列出业务语义不可动项；验收必须可测可量化；回滚预案至少一种。
- **FE**：只动前端层，不自行改后端字段/接口签名；严格走项目封装的 API 契约；不各自吞异常。
- **BE**：产出「原住民代码」（贴合本项目既有风格）；高并发扣减/原子性必须在真相源处完成。
- **QA**：命中任意 🔴 红线直接打回，不协商；不放行「没跑起来验证」的改动。
- **AI**：辅助实现与核查，但**不得替用户拍板技术选型/命根子判定**；动手前必须先复述改动范围。

## 不确定就问（agent 必须向用户确认的事项）

> 凡命中以下任一条，**停下来问用户**，不要替用户做技术决策或擅自假定。

- [ ] **产品方向不明确**（greenfield 框架选型前）：做什么、给谁用、核心差异点都没说清。
- [ ] **技术栈 / 框架有歧义**：用户没指定栈，且无法从现有代码推断。
- [ ] **高风险定级边界不清**：拿不准某改动是否 🔴（动钱/货/并发/幂等）。
- [ ] **Spec「不改什么」拿不准哪些是命根子**：不确定哪些链路/语义绝对不能动。
- [ ] **风格约束无法从代码推断**：项目代码太少/太乱，derive 不出可靠约定。
- [ ] **验收标准不可测**：用户给的是「体验更好」这类无法量化验证的描述。
- [ ] **回滚预案缺失**：改坏了没有明确的退路（revert / 开关 / 修复脚本）。
- [ ] **部署实例范围不确定**：拿不准目标代码跑在「单实例」还是「集群多实例」——直接决定锁选型，猜错会超卖。
- [ ] **池参数 / 拒绝策略无基线**：不确定线程池 core/max/queue、拒绝策略、连接池上限。
- [ ] **JVM 基线参数缺失**：生产 `-Xms/-Xmx`、GC 选型、是否开 OOM dump 无现成值。
- [ ] **你想替用户拍板技术决策但没把握**：选型、真相源判定、红线取舍、注入/锁/池选型等。

**提问格式建议**：给出「我的倾向 + 理由 + 备选」，让用户做选择题而非开放题。
