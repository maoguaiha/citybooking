# 📚 shared/ · 共享方法论文档（两分支共用）

> 本目录存放流水线的「查证手册与方法论」，已**内置在每个分支文件夹的 `参考文件/` 里**，使每个文件夹**自包含、可单独交给 Agent 全自动运行**（入口为 `../执行材料/RUN.md`，不需要项目根目录的 `00-ENTRY.md` 或其它文件）。
> 「项目根 + 多分支」统一编排模式下，根目录 `sync-shared.py` 可把本目录改动同步到各分支；纯自包含交付时该脚本不需要。

## 1. 三层结构总览

```
控制层（自包含文件夹内；根编排模式下才由 00-ENTRY.md 选分支）
├── 执行材料/RUN.md   自驱循环入口：反复执行直到 done / blocked（自包含交付用这个）
├── 运行时/STATE.md         状态机落地（task_id / 分支 / 节点 / Phase / 阻塞）
└── 运行时/PROJECT-FLOW.md  本项目工作项流程表（节点1~N + 每节点测试门 + 风险标记）

分支层（自包含流水线，每个文件夹含 01-init→02-spec→03-coding→04-review→[05-deploy]）
├── greenfield/   greenfield：A0→A1→A2→A3→A4→A5→A6→A7
└── brownfield/   brownfield：  B0→B1→B2→B3→B4→B5→B6

共享层（本目录）
├── redlines.md       十七维红线清单（grep 三连）
├── spec-template.md  项目信息卡 + Spec 五段 + §7.0 必带项 + 占位符清单
├── git-usage.md      Git 规范 + 使用规范 10 条
└── roles.md          RACI + 各角色红线 + 文档产出地图 + 不确定就问
```

## 2. 通用开发循环（两分支共用主轴）

```
需求/选型 ─▶ 定级 ─▶ 写 Spec/PRD ─▶ 编码(贴风格约束) ─▶ 单测(焊红线) ─▶ 节点测试门+验收确认
                                                          │
                      合并+沉淀 ◀── 红线审查 ◀── 上线验证(05,核心/高风险) ◀── 不通过则停留本节点
```

- **文档**在 Spec/PRD、提交信息、单测、MR 描述、合并记录处生成。
- **代码**在编码步生成，**可审计历史**在 Git 步生成，**作品/复盘**在合并/上线步生成。

## 3. 双层状态机（本模板的核心）

```
外层：遍历 PROJECT-FLOW.md 的节点 1 → N（工作项轴）
  └─ 内层：对每个节点跑 Phase 1→5（过程轴）
       01-init → 02-spec → 03-coding → [节点测试门+验收确认] → 04-review →(核心/高风险)→ 05-deploy
                                                       ↑ fail 停留 03-coding 改

- **Phase** = 过程阶段（文件名 01-init~05-deploy）。**05-deploy 仅核心/高风险节点触发**，普通节点跳过。
- **节点** = 工作项（来自 PROJECT-FLOW.md，如「用户注册」「下单」），编号 节点1~N。
- 二者永不混用同一词，避免你之前感到的「乱」。
```

## 4. 节点测试门 + 验收确认（Phase 3 末尾关卡）

编码 + 单测完成后，必须过**本节点测试门 + 验收确认**，才能进 04-review：

| 节点类型 | 测试门内容 | 通过标准（要可运行，不要"手动"） |
| --- | --- | --- |
| 普通节点 | 单测全绿 + 该节点接口/流程冒烟 | 单测 0 失败；核心路径冒烟命令/curl/端到端脚本绿 |
| 复杂 / 核心节点 | 上式 + **集成测试 + 验收测试** | 跨模块/跨服务链路通；[Spec 验收标准](spec-template.md)逐条核对通过 |

- **fail** → 输出 `[SYS: 节点N测试未过，停留 03-coding 修改]`，回 03-coding 改，不前进。
- **pass** → 进 04-review。
- **验收确认（Phase 4 合并前关卡）**：复杂/核心节点必须由 **PM/用户** 对照 Spec「验收标准」**逐条确认**；不通过退回 03-coding。低风险节点由 agent 自检 + 冒烟即可。

## 5. [SYS:] 握手码约定（Agent 状态变更通知）

| 时机 | 握手码 |
| --- | --- |
| ENTRY 选定分支 | `[SYS: 已选定分支=greenfield/brownfield，进入 <文件夹>/01-init]` |
| 初始化完成 | `[SYS: 阶段 01 结束，已自动流转至 02-需求拆解]` |
| Spec 确认 | `[SYS: 阶段 02 结束，契约已锁定，已自动流转至 03-编码执行]` |
| 编码+单测完成 | `[SYS: 阶段 03 结束，代码已暂存，进入节点测试门]` |
| 测试门 fail | `[SYS: 节点N测试未过，停留 03-coding 修改]` |
| 红线违规 | `[SYS: 审查不通过，退回 <文件夹>/03-coding 重新编码]` |
| 审查全绿+验收确认 | `[SYS: 阶段 04 结束，已合并，进入 05-上线验证]`（仅核心/高风险）/ `[SYS: 节点N通过，流转至节点N+1]` |
| 上线验证失败 | `[SYS: 上线验证失败，退回 <文件夹>/03-coding]` |
| 全部节点通过 | `[SYS: 全部节点通过，流水线执行完毕]` |

## 6. 状态机维护铁律（每个 Phase 流转前必做）

- **强制写回 STATE.md**：进入/离开任一 Phase，都把 `task_id / branch / current_node / phase_pointer / node_status / last_sys` 写回 STATE（不要只记在脑子里）。这是「续跑 / 挂起恢复」能成立的唯一前提。
- **task_id 绑定**：STATE 用 `task_id` 绑定当前需求/issue，同项目并行多需求时各自独立 STATE，互不踩踏。
- **挂起恢复**：命中「不确定就问」→ `blocked:true`+`block_reason` 并**立即停止**等用户；用户回复后，清 `blocked`、从断点 `phase_pointer` **原样续跑**（不重跑已完成 Phase）。

## 7. 闭环关键

合并/上线步沉淀的「AI 在哪坑过我」案例，写回 `spec-template.md` 的 Spec「不改什么」示例库，并刷新 `占位符清单` 锚点——**越用越懂你的项目**。这是本模板能跨项目复用同一套方法论、差异只在项目信息卡与 derive 出的风格/红线的根本原因。
